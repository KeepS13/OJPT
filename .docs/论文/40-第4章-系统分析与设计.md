# 4系统分析与设计

## 4.1系统总体架构设计

OJPT采用前后端分离架构，整体由浏览器前端、后端服务、关系数据库、缓存服务和Docker判题环境组成。前端层负责页面展示、路由跳转、登录状态维护、接口请求封装和用户交互，普通用户通过前端访问题库、做题页和个人中心，管理员通过前端访问管理后台。后端服务层负责业务处理和接口响应，覆盖认证、题库、做题、用户中心和管理端等业务。数据层由MySQL和Redis构成，MySQL保存用户、题目、标签、测试用例、代码草稿、提交记录和用户进度等核心业务数据，Redis用于保存刷新令牌和访问令牌黑名单等临时认证状态。Docker判题环境独立执行用户代码，后端根据执行结果更新提交记录和用户进度。系统总体架构如图4-1所示。

## 4.2系统部署结构设计

本地开发和演示环境中，前端Vite服务运行在`8110`端口，后端SpringBoot服务运行在`8111`端口，MySQL、Redis和Docker作为后端依赖服务运行。用户通过浏览器访问前端页面，前端通过HTTP API调用后端接口。部署设计要求前端服务和后端服务解耦，便于分别启动、构建和调试；后端统一连接MySQL和Redis，数据库结构由Flyway migration管理；Docker判题环境由后端调度，不直接暴露给普通用户；管理端可以检查Docker可执行文件、版本和镜像状态；上传头像等静态资源需要有稳定的服务端存储路径和访问路径。系统部署结构如图4-2所示。

## 4.3系统模块设计

根据系统业务流程，OJPT可以划分为认证与账号模块、普通用户模块、题库模块、做题与判题模块、训练数据模块、管理员模块和部署运行模块。

表4-1系统模块设计表

| 模块 | 主要功能 | 相关页面或接口 |
| --- | --- | --- |
| 认证与账号模块 | 登录、注册、刷新令牌、退出登录、当前用户、密码重置申请 | `/api/auth/*`，登录弹窗，注册表单 |
| 普通用户模块 | 个人资料、头像、账号安全、账号注销 | `/api/users/me/*`，个人中心 |
| 题库模块 | 题目列表、题目详情、公开样例、筛选分页 | `/api/problems/*`，题库列表，做题页 |
| 做题与判题模块 | 代码草稿、运行代码、正式提交、提交详情 | `/api/problems/run`，提交接口，做题页 |
| 训练数据模块 | 提交记录、训练看板、题目进度 | `/api/users/me/submissions`，训练看板 |
| 管理员模块 | 用户、题目、测试用例、标签、统计、密码重置审核 | `/api/admin/*`，管理后台 |
| 部署运行模块 | 前后端启动、数据库、缓存、Docker镜像、健康检查 | Actuator，判题环境健康检查 |

模块之间的关系以题库和判题为核心。题库模块提供题目数据，做题与判题模块产生提交记录和用户进度，训练数据模块读取提交和进度数据，管理员模块维护题库基础数据和判题环境。

## 4.4数据库概念结构设计

OJPT数据库概念结构围绕用户、题目、标签、测试用例、代码草稿、提交记录、提交用例结果和用户题目进度展开。各实体属性图和整体E-R图均依据当前Flyway migration和实体类整理。

### 4.4.1用户实体

用户实体用于保存登录账号、联系方式、头像、状态和角色等信息。用户扩展资料通过`user_profile`表维护，密码重置申请通过`password_reset_request`表维护。用户状态包括禁用、启用和待审核，角色主线包括普通用户`USER`和管理员`ADMIN`。管理员可以修改用户状态，系统登录逻辑需要根据用户状态决定是否允许进入系统。用户实体属性图如图4-3所示。

![图4-3用户实体属性图](../功能说明书/assets/figures/paper/fig-4-3-user-entity.png)

图4-3用户实体属性图

### 4.4.2题目实体

题目实体保存题号、标题、难度、题面Markdown、时间限制、内存限制、状态、提交次数和通过次数等信息。题目状态包括`DRAFT`、`PUBLISHED`和`ARCHIVED`。题号`problem_no`是普通用户浏览和做题路由的重要标识，前端以`P0001`等形式展示。只有已发布题目作为普通用户题库主列表内容展示，草稿和归档题目主要由管理员维护。题目实体属性图如图4-4所示。

测试用例实体保存题目输入、期望输出、用例类型、解释说明和排序信息。用例类型包括公开样例`SAMPLE`和隐藏用例`HIDDEN`。公开样例用于题目展示和用户试运行，隐藏用例用于正式提交判题。隐藏用例结果展示时需要避免泄露输入和期望输出。测试用例实体属性图如图4-6所示。

提交记录实体保存正式提交的源代码、语言、状态、运行耗时、内存、编译信息、判题信息和提交时间。提交状态包括`QUEUED`、`RUNNING`、`AC`、`WA`、`TLE`、`MLE`、`RE`、`CE`和`SYSTEM_ERROR`。提交记录是训练看板、提交历史和题目进度更新的重要依据。提交记录实体属性图如图4-8所示。

## 4.6 JWT鉴权与权限控制设计

用户登录成功后，后端生成访问令牌和刷新令牌并返回给前端。前端在请求需要认证的接口时携带访问令牌。后端过滤器解析令牌、检查令牌有效性和黑名单状态，并将用户身份写入安全上下文。访问管理员接口时，系统还会校验用户是否具有`ADMIN`角色。权限设计分为公开访问、登录访问和管理员访问三类：首页、题库列表、已发布题目详情和公开样例允许匿名访问；个人中心、代码草稿、运行代码、正式提交、提交详情、训练看板和提交记录需要登录；用户管理、密码重置审核、题目管理、标签管理、统计概览和判题环境健康检查需要管理员角色。JWT鉴权流程如图4-12所示。

## 4.7核心业务流程设计

系统核心业务流程包括登录认证流程、题库筛选流程、做题页初始化流程、代码运行流程、正式提交判题流程和管理员题目维护流程。

登录认证流程中，用户输入账号和密码，后端校验账号、密码和用户状态，成功后返回令牌和用户信息，失败时返回错误信息。题库筛选流程中，用户输入关键词、难度、标签、状态和分页参数，后端查询符合条件的题目并返回分页结果。做题页初始化流程中，前端按题号加载题目详情、公开样例和代码草稿。

代码运行流程中，用户选择语言并提交源代码和测试用例，后端调用Docker环境执行代码，返回运行结果。正式提交判题流程中，后端创建提交记录，进入判题执行，保存逐用例结果，更新提交状态和用户题目进度。管理员题目维护流程中，管理员新建题目草稿，编辑题面和限制，维护测试用例，绑定标签，并根据需要发布或归档题目。
