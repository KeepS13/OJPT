# OJPT 论文写作方案

本文档面向 OJPT 当前代码库和功能说明书，给出论文写作主线。论文应围绕在线编程训练平台展开，不把代码中历史保留的学校、院系、班级模型作为主线功能。

## 1. 论文题目

推荐中文题目：

> 基于 Spring Boot 的在线编程训练平台设计与实现

推荐英文题目：

> Design and Implementation of an Online Programming Training Platform Based on Spring Boot

题目说明：

1. `Spring Boot` 是后端主体技术，应体现在题目中。
2. `在线编程训练平台` 能覆盖题库、做题、运行、提交、训练数据和管理端。
3. 若导师强调题目长度，可写作 `基于SpringBoot的在线编程训练平台设计与实现`，减少空格占用。
4. 不建议使用 `OJPT` 作为论文题目核心词，因为缩写不够通用，摘要中可解释系统名称。

## 2. 摘要写作要点

中文摘要建议三段：

1. 第一段说明背景：在线编程训练、算法学习、自动判题、题库管理和训练反馈的需求。
2. 第二段说明系统内容：用户认证、题库检索、题目详情、代码编辑、草稿保存、样例运行、正式提交、Docker 判题、个人训练看板、管理员题库和用户管理。
3. 第三段说明技术路线与结果：Spring Boot、Vue 3、MySQL、Redis、Docker、JWT、Vitest/JUnit 测试，最终实现平台核心功能并通过测试验证。

关键词建议：

> 在线判题；Spring Boot；Vue；Docker；代码评测

英文关键词对应：

> Online Judge; Spring Boot; Vue; Docker; Code Evaluation

## 3. 总体章节结构

推荐使用 7 章结构：

| 章节 | 标题 | 核心任务 |
| --- | --- | --- |
| 1 | 绪论 | 说明背景、意义、国内外现状、研究内容和论文结构 |
| 2 | 相关技术和理论概述 | 说明支撑系统实现的技术和软件工程理论 |
| 3 | 系统需求分析 | 从用户、管理员、业务流程、非功能需求说明系统要做什么 |
| 4 | 系统分析与设计 | 说明架构、模块、数据库、接口、安全和判题流程如何设计 |
| 5 | 系统的开发设计与实现 | 结合截图和代码逻辑说明核心模块如何实现 |
| 6 | 系统测试 | 说明测试环境、功能测试、接口测试、单元测试和结果分析 |
| 7 | 结论 | 总结完成内容、不足与展望 |

## 4. 第 1 章 绪论

建议二级标题：

1. `1.1 研究背景与意义`
2. `1.2 国内外研究现状`
3. `1.3 研究内容与技术路线`
4. `1.4 论文结构安排`

写作要点：

1. 背景：编程能力训练、算法学习、在线评测、即时反馈、题库管理。
2. 痛点：传统本地运行结果不可统一评测，训练记录分散，题目维护成本高，教师或管理员难以维护题库质量。
3. 意义：提高刷题效率，统一代码运行环境，沉淀训练数据，支撑题库维护和判题环境检查。
4. 国内外现状：LeetCode、洛谷、Codeforces、在线教育平台、自动判题系统、代码沙箱安全。
5. 技术路线：前后端分离、RESTful API、JWT 鉴权、Docker 隔离执行、数据库持久化、前后端测试。

可引用资料：

1. `.docs/功能说明书/00-项目功能总览.md`
2. `.docs/功能说明书/03-做题与判题功能.md`
3. `.docs/功能说明书/08-部署与运行依赖.md`

应放图表：

1. 可放 `图1-1 在线编程训练平台业务闭环图`。
2. 可放 `表1-1 传统编程训练方式与在线判题平台对比`。

## 5. 第 2 章 相关技术和理论概述

建议二级标题：

1. `2.1 Spring Boot 框架`
2. `2.2 Vue 3 前端框架`
3. `2.3 MySQL 数据库`
4. `2.4 Redis 缓存与会话支撑`
5. `2.5 JWT 身份认证机制`
6. `2.6 Docker 容器化判题环境`
7. `2.7 软件测试技术`

写作要点：

1. 技术介绍必须服务于系统实现，不写泛泛百科。
2. Spring Boot 重点写分层开发、Controller-Service-Mapper、RESTful API。
3. Vue 3 重点写组件化、Composition API、路由、状态管理和交互。
4. MySQL 重点写结构化存储、事务、一致性和索引。
5. Redis 重点写 token 刷新、黑名单或会话辅助能力，按项目实际说明。
6. JWT 重点写无状态鉴权、Bearer Token、角色权限。
7. Docker 重点写代码执行隔离、语言镜像、资源限制、判题安全边界。
8. 测试技术写 JUnit、MockMvc、Vitest、组件测试、构建验证。

可引用资料：

1. `.docs/功能说明书/05-接口功能清单.md`
2. `.docs/功能说明书/08-部署与运行依赖.md`
3. 后端 `pom.xml`、前端 `package.json`。

应放图表：

1. 可放 `表2-1 系统主要技术栈表`。
2. 可放 `图2-1 前后端分离调用关系图`。

## 6. 第 3 章 系统需求分析

建议标题结构：

1. `3.1 系统功能分析`
2. `3.1.1 系统功能介绍`
3. `3.1.2 系统功能模块分析`
4. `3.2 系统功能流程介绍`
5. `3.2.1 系统数据流分析`
6. `3.2.2 数据字典`
7. `3.3 非功能需求分析`

功能需求应覆盖：

| 模块 | 需求说明 |
| --- | --- |
| 认证与账号 | 登录、注册、Token 刷新、退出、当前用户信息、忘记密码和审批 |
| 题库浏览 | 题目列表、关键词搜索、难度筛选、状态筛选、标签筛选、分页 |
| 题目作答 | 题面展示、语言选择、代码编辑、快捷键、草稿保存、测试用例编辑 |
| 代码运行 | 用户自定义输入与期望输出，后端返回各用例结果 |
| 正式提交 | 创建提交记录、异步判题、轮询结果、展示通过情况 |
| 训练数据 | 训练看板、提交记录、个人资料、账号安全 |
| 管理端 | 用户管理、题库管理、题目编辑、测试用例维护、标签管理、判题环境健康 |

非功能需求应覆盖：

1. 安全性：JWT 鉴权、角色权限、管理员接口限制、Docker 隔离执行。
2. 可用性：题库筛选、编辑器快捷键、草稿自动保存、错误信息复制。
3. 可维护性：前后端分离、接口分层、统一返回结构、功能文档。
4. 可靠性：单元测试、构建验证、判题环境健康检查。
5. 性能：分页查询、Docker 执行超时和内存限制、前端防抖保存。

## 8. 第 5 章 系统的开发设计与实现

建议二级标题：

1. `5.1 认证与账号模块实现`
2. `5.2 题库浏览模块实现`
3. `5.3 题目作答模块实现`
4. `5.4 代码运行与提交模块实现`
5. `5.5 个人中心模块实现`
6. `5.6 管理端模块实现`
7. `5.7 判题环境健康检查实现`

写作方法：

1. 每个模块按 `功能目标 -> 页面或接口设计 -> 核心实现 -> 运行效果` 写。
2. 页面截图应跟文字对应，不要只堆截图。
3. 后端实现写 Controller、Service、Mapper 或 Judge Service 的职责，不贴大段源码。
4. 前端实现写 Vue 页面、路由、组件状态、API 调用和关键交互。
5. 做题页是论文重点，应写代码编辑器快捷键、草稿保存、测试用例编辑、运行结果弹窗、提交结果轮询。

建议二级标题：

1. `6.1 测试方法`
2. `6.2 测试环境`
3. `6.3 功能测试`
4. `6.4 接口测试`
5. `6.5 单元测试`
6. `6.6 测试结果分析`

测试内容：

1. 功能测试：登录、注册、题库筛选、题目作答、运行、提交、个人资料、管理端题目维护。
2. 接口测试：认证接口、题库接口、运行提交接口、管理端接口。
3. 前端单元测试：ProblemSolveView 快捷键、测试用例模型、ProblemSetView 筛选。
4. 后端单元测试：认证、管理员权限、题库、提交、判题环境。
5. 构建验证：前端 `npm.cmd run build`、后端 Maven test。

测试结果写法：

1. 不要只写“测试通过”，应写输入、操作、期望结果、实际结果。
2. 对失败场景也要覆盖，如密码错误、空输入、代码运行错误、未登录访问、权限不足。
3. 单元测试结果可写测试数量、核心断言和通过情况。

## 10. 第 7 章 结论

建议二级标题：

1. `7.1 主要工作总结`
2. `7.2 系统不足`
3. `7.3 后续展望`

总结应覆盖：

1. 完成在线编程训练平台的认证、题库、做题、运行、提交、训练数据和管理端。
2. 完成基于 Docker 的多语言代码运行与评测。
3. 完成题库维护、测试用例维护、标签管理和判题环境健康检查。
4. 完成前后端测试与构建验证。

不足可写：

1. 代码编辑器仍基于 textarea，复杂语法高亮和智能提示能力有限。
2. 判题资源隔离策略仍可进一步细化。
3. 题目推荐、训练路径规划和难度自适应能力有待增强。
4. 大规模并发判题下的队列调度和监控能力仍可扩展。

展望可写：

1. 引入更完整的代码编辑器能力。
2. 完善判题队列和监控。
3. 增加题目推荐和错题分析。
4. 支持更多语言和更细粒度沙箱策略。

## 11. 写作边界

必须避免：

1. 把历史保留的学校、院系、班级模型写成当前系统主线。
2. 写没有实现的在线课堂、教师批改、班级作业、课程管理。
3. 把 Swagger、Actuator、Docker 等截图当成设计图。
4. 大段复制代码。
5. 用营销式语言替代软件工程论证。
6. 编造性能数据、用户规模或生产部署效果。

可以写：

1. 当前已实现的用户、管理员、题库、做题、提交、训练数据、管理端能力。
2. 当前已存在的接口、数据表、测试用例和截图。
3. 明确标注为“后续展望”的未实现能力。
